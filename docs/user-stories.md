# User Story: Cherry Pick — целевой продукт

Документ описывает, как продукт должен выглядеть в конечном результате,
и разделяет это на «уже реализовано» и «надо построить».

Источник истины по текущему состоянию — код в `src/fashion_agent/`.
Ссылки вида `файл:строка` указывают на текущую реализацию.

## 1. Что уже реализовано сегодня

| Область | Состояние |
|---|---|
| Граф | LangGraph, 14 узлов, один линейный проход: `extract_request → [уточнения] → knowledge → search_plan → параллельный поиск → атрибуты → ранжирование → сборка → критика → показ` (`graph.py:45-164`) |
| Диалог | Веб-чат на голом `ThreadingHTTPServer`, сессия в cookie, чекпойнтер `InMemorySaver` (`web.py:801`, `graph.py:40`) |
| Извлечение запроса | LLM превращает переписку в `StylingRequest` (повод, бюджет, город) и задаёт до 2 уточняющих вопросов (`basic_requests.py:25-91`) |
| Профиль предпочтений | `StylePreference` (цвет/силуэт/посадка/материал/рисунок/деталь/бренд/стиль) + извлечение из каждой реплики (`styleDNA.py:14-97`) |
| Тест вкуса | Сравнение пар картинок из `outfit_cards/`, 6 пар, эвристика `inferred_preferences` со снимками атрибутов, SQLite `data/taste.sqlite3` (`taste_quiz.py`, `taste_conversation.py`) |
| Галерея | `/cards` — 71 карточка, поиск и фильтр по стилю на клиенте (`taste_catalog_web.py`) |
| База знаний | 10 стилей, 11 формул образа, **3 тренда** в статичных JSON (`knowledge/data/*.json`) |
| Ретрив знаний | Ключевой + fuzzy (`difflib`), без эмбеддингов и вектора (`knowledge/retrieval.py:76-118`) |
| Поиск товаров | Единственный источник — SerpApi `google_shopping`, максимум 10 товаров на категорию, без пагинации и ретраев (`product_search/tools.py:35-204`) |
| Ранжирование | `style_score + request_score + retrieval_score`, жёсткий отсев по `dislike` (`products_processing.py:13-107`) |
| Сборка образа | Детерминированный полный перебор комбинаций, бюджетные проверки, топ-8 (`outfits/builder.py:24-246`) |
| Критика | LLM-критик по тексту и атрибутам, 4 оценки 0-10, `approved` (`outfits/critique.py:71-231`) |
| Показ | Карточки + коллаж через Playwright + `rembg` (`web.py:687-718`, `web_collage.py`) |
| Тесты | 10 файлов, 1566 строк, включая E2E на Playwright |

### Критичные пробелы текущей версии

1. **LLM без зрения.** `ChatDeepSeek(deepseek-v4-flash)` — только текст (`llm.py:34-39`).
   Загрузить фото пользователя и оценить его нечем.
2. **Ни одного загрузчика файлов**, нет multipart, нет хранилища пользовательских фото.
3. **Город теряется при поиске.** `params["location"] = location` и тут же
   `params.pop("location", None)` (`product_search/tools.py:84-90`) — до SerpApi доходит
   только `gl=ru`, выданный по `locale`.
4. **Нет размеров.** Ни в профиле, ни в запросе, ни в фильтрах SerpApi.
5. **Профиль в памяти процесса.** `InMemoryStore` (`graph.py:39`) — предпочтения
   переживают только текущий процесс; `store.search(limit=100)` молча обрезает.
6. **Знания не обновляются.** `get_knowledge_repository()` под `@lru_cache` (`knowledge/repository.py:165`),
   планировщика нет, все 3 тренда протухают 2026-12-31.
7. **Атрибуты товаров выдумываются LLM** из title и snippet
   (`products_processing.py:130-155`) — на этом стоят все скоринги.
8. **Ретрив знаний зависит только от `vibe`.** Пустой `vibe` → пустые стили,
   пустые формулы, пустые тренды (`knowledge/retrieval.py:184-185`, `222-223`).
9. **Авторизации нет.** `user_id` вводится руками в UI и хранится в `localStorage` (`web.py:557-580`).
10. **Два конкурирующих онбординга**: `TasteConversation` и `GuidedStyling`
    (`guided_styling.py:23`), второй перехватывает каждое сообщение.

## 2. Продуктовая цель

Персональный стилист, который ведёт долгий диалог, помнит клиента, следит за
трендами, работает с его реальным гардеробом, умеет оценить присланное фото и
дотянуть образ до покупок в интернете.

**Персона.** Клиент 25-40 лет, одевается сама, стесняется спросить в магазине,
покупает 5-15 вещей в сезон, пользуется телефоном, не хочет заполнять анкеты.

**Главная ценность.** «Я скинула фото того, что ношу, и получила образ, который
реально собрать из того, что у меня уже есть, плюс понимание, что купить».

## 3. Эпики и user stories

Приоритет: **P0** — без этого продукт не работает, **P1** — следующий этап,
**P2** — развитие.

---

### US-01 (P0). Долговременный диалог и память о клиенте

**Как** клиент, **я хочу** просто разговаривать с Cherry и не отвечать на анкеты,
**чтобы** она постепенно поняла мой вкус.

**Критерии приёмки**

- Диалог идёт в обе стороны: агент задаёт уточняющие вопросы, реагирует на
  уточнения, помнит сказанное в предыдущих сессиях.
- Из каждой реплики извлекаются устойчивые предпочтения, но **не** разовые
  («сегодня хочу чёрное» ≠ «ненавижу белое»). Нужны правила `decay` и
  `revoke`: предпочтение можно снять фразой «я передумала, ненавижу чёрное».
- Профиль переживает перезапуск сервера (сейчас `InMemoryStore` — нет).
- Агент может объяснить, как понял клиента, и попросить подтвердить.
- Нет жёстких анкет на старте: онбординг — в диалоге, с предложением, а не условием.
- Диалог с агентом не перехватывается мастерами (`GuidedStyling` сейчас
  перехватывает каждое сообщение — `guided_styling.py:104-108`).

**Уже есть:** извлечение предпочтений, чекпойнтер диалога, уточняющие вопросы.
**Надо:** персистентный стор профиля, правила обновления/ослабления, слияние
одного источника онбординга, команда «что ты обо мне знаешь».

---

### US-02 (P0). Регулярное обновление знаний о трендах

**Как** клиент, **я хочу**, чтобы Cherry знала, что сейчас актуально,
**чтобы** не предлагать образ двухлетней давности.

**Критерии приёмки**

- Есть процесс обновления: по расписанию или по кнопке, а не только ручная
  правка JSON.
- Источники: Pinterest Predicts, подборки магазинов, фэшн-медиа, RSS/публичные
  ленты. У каждой записи тренда — **ссылка на источник и дата** (сейчас
  `source_urls: []` у всех 10 стилей, у трендов ровно одна ссылка).
- Новые тренды не перезаписывают старые: версионирование, `valid_from`/`valid_until`,
  архив протухших трендов.
- Тренды привязаны к региону и сезону пользователя, а не к серверу
  (`infer_regions` сегодня знает только Москву и Россию — `knowledge/retrieval.py:53-73`).
- Агент умеет объяснить, **почему** предлагает элемент: «это тренд сезона,
  источник — ...».
- База знаний (стили, формулы, тренды) пополняется с разбором новых источников
  автоматически, а не «10 стилей навсегда».

**Уже есть:** модели `StyleCard` / `OutfitFormula` / `TrendCard` с полем
`sources`, скоринг трендов в образе (`outfits/scoring.py:204-260`).
**Надо:** сборщик данных, планировщик, валидация новых записей, региональность.

---

### US-03 (P0). Обучение на фотографиях образов

**Как** клиент, **я хочу** показать Cherry фотографии образов, которые мне
нравятся (а с 2024 года — и не нравятся), **чтобы** она поняла вкус быстрее,
чем по текстовым вопросам.

**Критерии приёмки**

- Загрузка своих фото в чат: drag&drop, выбор из галереи телефона, вставка из
  буфера обмена.
- Агент анализирует картинку vision-моделью и извлекает те же признаки, что и
  каталог: `color`, `silhouette`, `fit`, `material`, `pattern`, `detail`, `item`,
  `style` — в общем словаре с карточками `outfit_cards`.
- Фото сохраняются в личном кабинете (`US-05`), привязаны к `user_id`,
  удаляются пользователем.
- Из анализа фото рождаются предпочтения с понятным пользователю объяснением:
  «нравится посадка, тренч, спокойная палитра».
- Работают оба сценария: **нравится** и **не нравится** (второй важнее).
- Возможность сравнить два присланных фото, как в текущем тесте пар.
- Рядом доступен текущий каталог на 71 карточку из `outfit_cards/` как разогрев:
  пара «своё фото / карточка из коллекции».
- Приватность: фото не уходят в поиск товаров и не показываются третьим лицам.

**Уже есть:** каталог 71 карточки с атрибутами, pairwise-эвристика
`inferred_preferences` (`taste_quiz.py:90-126`), механика пар и профиля.
**Надо:** vision-модель, загрузка файлов, персистентное хранилище фото,
объединение источников сигнала (`pairwise`, `image`, `explicit`) с приоритетами.

### US-04 (P0). Качественный поиск товаров

**Как** клиент, **я хочу** получать релевантные товары, а не странные ссылки,
**чтобы** не тратить время на листание мусора.

**Проблема сегодня.** Товары приходят странными, потому что:

| Причина | Место |
|---|---|
| Город выбрасывается перед запросом к API | `product_search/tools.py:90` |
| `gl`/`hl` берутся из `locale`, а не из города клиента | `product_search/tools.py:60-74` |
| `max_price` не поддерживается движком — бюджет не фильтруется на входе | `product_search/tools.py:87-88` |
| Товары в чужой валюте молча выбрасываются | `product_search/tools.py:163-164` |
| Никаких фильтров: бренд, размер, цвет, цена, наличие | целиком |
| Размеров одежды в системе нет вообще | `states.py:55-84` |
| Атрибуты выдумываются из title, а не из страницы товара или фото | `products_processing.py:130-155` |
| Жёсткий лимит 10 товаров на категорию, без пагинации | `product_search/tools.py:201-202` |
| Одна ошибка API валит весь ход графа | без ретраев |
| Лучшие 4 товара на категорию попадают в сборку | `outfits/builder.py:55` |

**Критерии приёмки**

- Город клиента реально влияет на выдачу (и приходит в API, а не удаляется).
- Бюджет, размер, цвет — фильтры на входе, а не пост-фильтр.
- **Генерация запроса переработана**: LLM даёт структурный фильтр
  (категория, размер, цена, цвет, бренд, ключевые слова), а не одну строку
  «на их языке»; отдельно — текст запроса для поисковой выдачи.
- Есть fallback-стратегия: если источник не дал результатов — другой источник,
  иначе — снятие фильтров по одному с явным сообщением, какой фильтр снят.
- Несколько источников за абстракцией, с возможностью заменить SerpApi
  (например, на маркетплейсы/агрегаторы) без переписывания графа.
- Ретраи с backoff, кэш ответов, обработка лимитов, логирование запроса.
- Атрибуты берутся из карточки товара (или из фото), а не выдумываются;
  неизвестное честно помечается `unknown`, а не заполняется.
- В выдаче видно, почему товар предложен: совпали фильтры, рейтинг, цена.
- Есть оценка качества: замер «доля релевантных из 10» на ручном наборе
  запросов как регрессионный тест.

**Уже есть:** `ProductSearchTask`, параллельный fan-out через `Send`
(`product_search.py:202-218`), скоринг, диагностика «ничего не нашлось».
**Надо:** слой источников, структурные фильтры, размеры, надёжность, метрики.

### US-05 (P0). Гардероб клиента

**Как** клиент, **я хочу** сфотографировать свои вещи и получить цифровой
гардероб в личном кабинете, **чтобы** агент знал, что у меня уже есть.

**Критерии приёмки**

- Загрузка фото вещи: камера с телефона, выбор файла, несколько фото одной вещи.
- Изображение обрабатывается: фон отделяется, вещь выравнивается, сохраняется
  нормализованная версия (сегодня `rembg` уже есть — `web_collage.py:46-61`).
- Vision-модель распознаёт: категорию, цвет, посадку/силуэт, материал, рисунок,
  детали, бренд, сезон, примерный размер, состояние.
- Клиент **подтверждает или правит** распознавание. Ошибка распознавания
  цвета в гардеробе — самая дорогая ошибка, поэтому ручное подтверждение
  обязательно и быстрое.
- Ведь хранится в личном кабинете: список, фильтры, поиск, редактирование,
  удаление, отметка «носится / не носится».
- Данные принадлежат клиенту: удаление аккаунта удаляет фото.
- Фото не уходят в поиск и третьим лицам.

**Уже есть:** только коллажная отрисовка. Загрузки, распознавания и
хранилища нет.
**Надо:** multipart-загрузка, объектное хранилище, таблица `wardrobe_items`,
vision-пайплайн, редактирование карточки вещи.

### US-06 (P0). Образ из своего гардероба + добор из интернета

**Как** клиент, **я хочу** собрать образ **из своих вещей** и получить список
того, что стоит купить, **чтобы** не тратить деньги на вещи, которые у меня уже есть.

**Критерии приёмки**

- Сборка образа из гардероба — основной сценарий, а покупки — дополнение.
- «Собери на встречу / на работу / на концерт» → образ минимум из вещей гардероба.
- Показывается, сколько вещей взято из гардероба, а что предлагается купить.
- Для недостающих категорий — поиск в интернете, но с учётом уже собранного:
  не предлагать второй чёрный низ, если чёрный низ уже есть.
- Уважается «используй обязательно» и «не хочу» (сейчас поля есть
  (`states.py:80-84`), но **нигде не используются**).
- Покупки дороже бюджета не выпадают молча — предлагается ослабление.
- Можно зафиксировать собранный образ и вернуться к нему позже.

**Уже есть:** `build_outfits` умеет собирать из товаров по формулам,
но про гардероб не знает.
**Надо:** источник «предмет из гардероба» в общей модели образа, приоритет
гардероба, связка `must_use` / `dislikes` с билдером.

### US-07 (P0). Оценка образа по фото клиента

**Как** клиент, **я хочу** скинуть фото того, как я оделась, и получить честную
оценку с подсказками, **чтобы** понять, что поправить.

**Критерии приёмки**

- Загрузка фото «мой образ» (селфи, фото с другими, зеркальное снимок).
- Агент описывает образ: вещи, цвета, пропорции, силуэт, обувь, аксессуары.
- Даёт оценку по понятным осям (попадание в повод, согласованность, сочетание
  цветов, силуэт, баланс) — в человеческих словах и баллах, как в
  `OutfitCritique`, а не «всё хорошо».
- Отдельно оценивает посадку и пропорции относительно фигуры клиента (US-09).
- Предлагает **конкретные** изменения: заменить обувь, убрать аксессуар,
  другой верх — с обоснованием и ссылкой, если вещь из гардероба.
- Предлагает пересобрать образ с учётом правок в один клик.
- Сравнивает «до / после».
- Честно говорит, чего не видно на фото (лицо, обувь, посадка сзади).

**Уже есть:** `OutfitCritique` с 4 осями и `approved` (`outfits/critique.py`),
но только по тексту и символьным атрибутам товаров, без картинки.
**Надо:** vision-оценка реального фото, связка с гардеробом и профилем фигуры,
итеративный цикл «оценили → поправили → переоценили».

### US-08 (P1). Доступ агента в интернет

**Как** клиент, **я хочу**, чтобы Cherry сама учитывала погоду и контекст,
**чтобы** не предлагать шубы в мае.

**Критерии приёмки**

- Инструмент погоды по городу клиента: температура, ощущается как, осадки,
  ветер; попадает в сборку образа (верхняя одежда, обувь, зонт).
- Планировка на день: «в 15:00 дождь, ветер 8 м/с» → адаптация.
- Агент умеет искать в интернете: тренды (связано с US-02), отзывы о бренде,
  наличие товара, актуальная цена.
- Каждый факт из интернета со ссылкой. Агент различает «знаю» и «проверила сейчас».
- Инструменты объявлены агенту явно, а не вызываются императивно: сейчас у
  графа **нет ни одного tool-call** (единственный `@tool` вызывается напрямую —
  `product_search/product_search.py:190`).
- Тул-колл ограничены по времени, повторяемости и безопасности (никакой
  произвольной генерации кода, файловой системы, запросов с приватными данными).
- Если инструмент недоступен — агент говорит об этом прямо, а не выдумывает погоду.

**Уже есть:** интерфейс `catalog_search` как образец инструмента.
**Надо:** погодный провайдер, поиск в интернете, tool-calling в графе,
правила цитирования и деградации.

### US-09 (P1). Тип фигуры и типаж

**Как** клиент, **я хочу**, чтобы агент знал мой тип фигуры и типаж,
**чтобы** советовал посадки и длины, которые сидят красиво.

**Критерии приёмки**

- Итоговый тест: **самоописание + фото**, а не «введите рост и вес»:
  - силуэт (тип фигуры): «песочные часы», «груша», «яблоко», «прямоугольник», «перевёрнутый треугольник», «ромб»;
  - пропорции: рост, длина ног относительно корпуса (по фото — «примерно»);
  - что клиенту нравится и что хочет скорректировать.
  - Отказ от точных замеров по фото — и явная оговорка об оценке «на глаз».
- Типаж: температура палитры (тёплый/холодный), контраст, насыщенность,
  рисунок; оформление (romantic/minimal/sportive/drama).
- Размеры одежды и обуви: текущий, обычный, как «между».
- Профиль применяется к рекомендациям: длина, посадка, высота каблука,
  ширина плеч, силуэт, палитра; **и** к оценке образа из US-07.
- Результат — не ярлык, а подсказки в понятных формулировках
  («у вас выраженная талия — подойдут пояса и приталенные силуэты»).
- Тест встраивается в диалог, результат можно пересмотреть и изменить.

**Уже есть:** ничего. Ни типа фигуры, ни размеров в модели.
**Надо:** модель профиля, сценарий теста, vision-оценка фото (мягкая,
с оговорками), применение в сборке и оценке.

### US-10 (P1). Личный кабинет

**Как** клиент, **я хочу** одно место, где видно всё обо мне, **чтобы**
не терять настройки между устройствами.

**Критерии приёмки**

- Регистрация и вход, профиль привязан к аккаунту, а не к ручному `user_id`
  в `localStorage` (`web.py:557-580`).
- Разделы: профиль и вкус, фигура и типаж, размеры, гардероб, сохранённые
  образы, история покупок, референсы образов.
- Возможность выгрузить и удалить все свои данные.
- Сессии переживают перезапуск сервера.

**Уже есть:** только session-cookie в памяти.
**Надо:** аутентификация, персистентное хранилище вместо `InMemoryStore`
и `InMemorySaver`.

## 4. Нефункциональные требования

- **Приватность.** Фото и профиль — данные клиента. Согласие на обработку фото,
  удаление по запросу, никакой передачи референсов в поиск товаров.
- **Устойчивость.** Внешний источник упал — агент отвечает, а не возвращает 500
  (сейчас `web.py:1117-1127` отдаёт сырое исключение).
- **Скорость.** Коллаж на Playwright + `rembg` сейчас считается синхронно в
  HTTP-обработчике (до 12 загрузок и 3 запуска Chromium на ответ) — нужно в фон
  и с кэшем.
- **Наблюдаемость.** Логи запросов к источникам, метрики качества поиска и
  покрытия знаниями, трассировка решений агента.
- **Прогон тестов.** `uv run pytest`, линт и тайпчек — обязательный шаг.

## 5. Открытые вопросы

1. **Источник товаров.** Оставляем SerpApi Google Shopping или переходим на
   агрегатор/собственный краулер карточек магазинов? Своё решение требует работы
   сrobots.txt, антиботом и юридической стороной.
2. **Размеры.** Размеры одежды конкретных брендов несовместимы. Достаточно ли
   общей сетки XS–XL плюс «примерно по фото», или нужна таблица по брендам?
3. **Vision-модель.** Текущий DeepSeek text-only. Нужен мультимодальный
   провайдер (или два: дешёвый для распознавания, сильный для оценки образа).
4. **Хранение.** SQLite достаточно для пилота, но фото и несколько пользователей
   быстро упрутся в файловую систему. S3-совместимое хранилище или локальный диск?
5. **Точность типа фигуры по фото.** Спорная вещь и репутационный риск. Ограничиться
   самоописанием, разрешить фото с явной оговоркой, или не делать вовсе?
6. **Порядок.** Что важнее для первого прогона: качество поиска (US-04) или
   гардероб + оценка образа (US-05..07)?
7. **Приватность референсов.** Каталог `outfit_cards` — локальный. Планируется ли
   публичная галерея, и не станет ли она проблемой при публичном запуске?
